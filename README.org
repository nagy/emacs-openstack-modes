#+title:    emacs-openstack-modes - OpenStack resource modes for Emacs
#+author:   Daniel Nagy
#+language: en

Emacs major modes for displaying OpenStack resources.

Every OpenStack resource has a unique ID.  This repository starts
with one base mode that handles the ID, so that future
resource-specific modes can depend on it.

* Usage

The package installs as =openstack=, the same name as its entry
library.  Requiring it loads the data layer, the base mode, the ID
cache and the resource types:

#+begin_src elisp
(require 'openstack)
#+end_src

With =use-package=:

#+begin_src elisp
(use-package openstack
  :config
  (setq openstack-refresh-interval 30))
#+end_src

=openstack-mode= stays a valid feature.  Requiring it loads only the
base mode and the data layer, without the resource types.  The
optional layers keep their own libraries: =openstack-xref=,
=openstack-url=, =ol-openstack= and =openstack-evil=.

Commands:

- =M-x openstack-mode= -- put the current buffer into the mode
- =M-x openstack-display= -- display a resource by ID in a
  dedicated buffer
- =M-x openstack-open-id= -- display any resource by ID; the
  type comes from the list cache, or the prompt
- =M-x openstack-read-refresh= -- refill the cached resource
  lists
- =M-x openstack-copy-id= (=c=) -- copy the resource ID to
  the kill ring
- =M-x openstack-open-web= (=w=) -- open the dashboard page
  for the resource
- =M-x openstack-pop= (=p=) -- pop back to the buffer the
  resource was displayed from
- =M-x openstack-go-to-parent= (=dired-jump=,
  =dired-up-directory=) -- open the view one level above the
  current buffer

Customization (=M-x customize-group openstack=):

- =openstack-buffer-name= -- prefix of the display buffer name;
  the resource ID is appended
- =openstack-web-base-url= -- base URL of the OpenStack
  dashboard
- =openstack-id-prefix= -- resource type path segments in the
  dashboard URL
- =openstack-url-suffix= -- path segments appended after the
  resource ID (e.g. =/detail=)
- =openstack-program= -- path to the =openstack= command line
  client (python-openstackclient)
- =openstack-resource-types= -- resource type, display mode and
  display command of every derived mode
- =openstack-resource-cache-ttl= -- seconds a cached
  client answer stays valid; =nil= keeps it forever
- =openstack-status-fields= -- fields rendered with a status
  face (=status=, =vm_state=, =host_status=, =health_status=)
- =openstack-status-faces= -- status value to face map
- =openstack-date-fields= -- fields rendered with the
  =openstack-date= face (=created_at=, =updated_at=,
  =launched_at=, =terminated_at=, =deleted_at=, =timestamp=);
  =nil= renders dates with the default face
- =openstack-reference-fields= -- fields whose values name
  other resources, one per line (=subnets= holds subnet IDs)
- =openstack-transitional-states= -- statuses that still
  change, so their buffer polls faster
- =openstack-refresh-fast-interval= -- seconds between refresh
  while a status still changes; =openstack-refresh-interval=
  stays the upper bound

* Finding resources

The display commands complete the resource ID from
=openstack server list= and friends.  The prompt offers the name
and the ID, so the name picks the resource:

#+begin_src elisp
  (openstack-server-display)   ; M-x, then pick web-1
#+end_src

A raw UUID typed at the prompt still works, and a failing client
falls back to a plain prompt.  The rows stay cached for
=openstack-resource-cache-ttl= seconds; =M-x openstack-read-refresh=
refills them.

=M-x openstack-open-id= displays any resource.  Without a type
it asks the cache, which runs =RESOURCE list= for each type in
=openstack-resource-types= until one holds the ID.

The xref backend makes =M-.= open the resource whose ID sits at
point, in any buffer: a log line, a mail, an Org document or a
rendered field.  It reads the =openstack-id= text property first
and a UUID under point second.  Enable it in your init file:

#+begin_src elisp
  (require 'openstack-xref)
#+end_src

The =M-?= prompt completes the cached IDs.

The same rule defines the =openstack-id= thing, so any package
reads the ID at point with =(thing-at-point 'openstack-id)= and
the bounds with =bounds-of-thing-at-point=.  Display buffers also
answer the =uuid= thing from the property, so a table column
truncated to the window width still yields the full ID.

=M-?= lists the resources that a cached list row mentions in one of
its fields, so a server leads to its image or its network.

The =openstack:= URL scheme opens a resource from any buffer: a
mail, a log line or =goto-address-mode=.  A URL is
=openstack:TYPE/ID= or =openstack:ID=:

#+begin_src elisp
  (require 'openstack-url)
#+end_src

=imenu= indexes the fields of a show buffer and the rows of a list
buffer, so =M-x imenu= or =consult-imenu= jumps to a field or to a
resource.  The ID prompt annotates each candidate with the fields
of =openstack-read-annotation-fields=, such as =ACTIVE= or =20=.

* Servers

=openstack-server-mode= is the first resource-specific mode
derived from the base mode.  It fetches the server with
=openstack server show= through the asynchronous CLI layer and
renders the server's fields, inheriting the ID handling, the
refresh pipeline and bookmark support:

- =M-x openstack-server-display= -- display a server by ID in a
  dedicated buffer

Customization (=M-x customize-group openstack-server=):

- =openstack-server-buffer-name= -- prefix of the server display
  buffer name; the server ID is appended
- =openstack-server-fields= -- fields shown first, in this
  order; all remaining fields follow, sorted by name

* Volumes and images

=openstack-volume-mode= and =openstack-image-mode= work exactly
like the server mode, for block storage volumes and disk images:

- =M-x openstack-volume-display= -- display a volume by ID
  (=openstack volume show=; dashboard prefix =volumes=)
- =M-x openstack-image-display= -- display an image by ID
  (=openstack image show=; dashboard prefix =images=)

A =properties= hash table -- the Glance image properties or the
Swift container properties -- prints as an indented block that
closes the table, one =key: value= line per property, sorted by
key, instead of one JSON dump.  The same holds for the Glance
=locations= list: the client flattens that attribute into
=properties=, so the block nests there and prints each location
as an indented record with its keys on their own lines.  A list
of plain values prints as comma-separated text: the =tags= of an
image read =subnet-1, subnet-2=
instead of a JSON array.  A field that =openstack-reference-fields=
names prints its IDs one per line instead, as the =subnets= of a
network do.  The
image =size= and =virtual_size= print human readable through
=file-size-human-readable=, for example =224M=, while the list
column keeps the raw byte count for sorting.

Each has its own =openstack-volume-buffer-name= /
=openstack-image-buffer-name= and =-fields= defcustoms.

* Networks

=openstack-network-mode= displays a network of the Networking
service:

- =M-x openstack-network-display= -- display a network by ID
  (=openstack network show=)

A network lists the subnets it owns.  The =subnets= field prints
one subnet ID per line, each with the =openstack-id= face and the
=openstack-id= text property: =RET= or =mouse-2= on such a line
opens the subnet.  No subnet mode exists yet, so the command
signals a =user-error= until one arrives.  A subnet mode that
=openstack-define-resource= defines makes these lines open the
subnet in its own buffer, without a change to the network mode.
The =openstack-reference-fields= defcustom maps a field name to
the resource type of its values; it holds the =subnets= entry.

Horizon shows a network below the project's network panel, so
this mode uses the URL suffix: the dashboard URL is
=project/networks/ID/detail=.  The =openstack-url-suffix=
defcustom carries the trailing segment; =openstack-id-prefix=
carries the leading ones.  Other modes leave the suffix empty.

* Projects

=openstack-project-mode= displays a project of the Identity
service:

- =M-x openstack-project-display= -- display a project by ID
  (=openstack project show=)

Horizon serves the project detail view below its own panel, so
this mode sets the full URL: =identity/projects/ID/detail=.  The
=parent_id= field stays plain text, because a top-level project
holds its domain ID there and a domain is not a resource type of
this package.  The =options= hash table prints as its JSON text;
a disabled project shows no =enabled= line, because the renderer
skips a false value, as it does for every boolean field.

* Object storage

=openstack-container-mode= displays a container of the Object
Storage service (Swift).  A container holds objects, and its
name is its identifier:

- =M-x openstack-container-display= -- display a container by
  name (=openstack container show=)

The mode passes the container name to the base mode as the
resource ID, because a Swift container has no UUID.  The ID
completion reads =openstack container list=, whose rows carry a
=Name= field and no =ID= field.  Horizon shows a container at
=project/containers/NAME=, so the mode sets
=openstack-id-prefix= and leaves =openstack-url-suffix= empty.

The S3 API of Swift is a second interface on the same service.
Its access key and secret come from =ec2 credentials= of the
Identity service; this package does not display them.

* Collection lists

Collection modes display a list of resources instead of a
single resource; the server list mode is the reference:

- =M-x openstack-server-list-display= -- list all servers as a
  table (=openstack server list=)
- =M-x openstack-volume-list-display= -- list all volumes
  (=openstack volume list=)
- =M-x openstack-image-list-display= -- list all images
  (=openstack image list=)
- =M-x openstack-network-list-display= -- list all networks
  (=openstack network list=)
- =M-x openstack-project-list-display= -- list all projects
  (=openstack project list=)
- =M-x openstack-container-list-display= -- list all containers
  (=openstack container list=)

Every list mode derives from =openstack-list-mode=, which derives
from =tabulated-list-mode=.  The table therefore has a clickable
column header, per-column sorting (=S= or a header click, a second
sort flips the direction), per-column resizing (={= and =}=) and
column widths that fit the window; a resize re-lays out visible
lists without a new CLI call.  The mode line shows the row count,
the sort column and the last fetch error, because the header line
carries the column labels.

RET or =mouse-2= anywhere on a row opens the resource's show
buffer: list modes bind =openstack-show-command= to their
resource's display command (e.g. =openstack-server-display=).  =c=
copies the ID of the row and =w= opens its dashboard page.  =n= and
=p= move by row, and =q= buries the buffer: =openstack-pop= (=p=)
stays a show-mode command.  The ID field line in show buffers works
the same way, and so does a subnet ID in a network buffer, which
opens through the display command of the type that
=openstack-reference-fields= names.

The list buffer has no resource ID: the buffer-level ID commands
do not apply there.  Columns come from the mode's =-fields=
defcustom (=openstack-server-list-fields=,
=openstack-volume-list-fields=, =openstack-image-list-fields=,
=openstack-network-list-fields=, =openstack-project-list-fields=,
=openstack-container-list-fields=)
first; all remaining fields
follow, sorted by name.  Sorting compares typed values, so a
numeric column such as =Size= sorts as numbers and shows
right-aligned.  A row identity is the resource ID; a container
row takes its name instead, because a Swift container has no
UUID.  =openstack-container-list-arguments= holds extra client
arguments for =container list= (=--long= by default, for the byte
and object counts).  =openstack-project-list-arguments= asks for
=--long= too, so the table shows the domain, the description and
the enabled flag, which the client omits by default.  The table
logic lives in the base mode
(=openstack-list-fetch=, =openstack-list-columns=,
=openstack-list-render=); list modes are thin wrappers over it,
like the show modes over =openstack-show-fetch=.

=C-u M-x openstack-image-list-display= lists hidden images too,
because the prefix argument appends =--all= to =image list= (after
=openstack-image-list-arguments=).  The image list forgets it on
the next call without a prefix.  No other resource maps the prefix
argument: =server list= and =volume list= offer =--all-projects=
(admin only), =network list= has no all switch.

* Going up one level

=M-x openstack-go-to-parent= opens the view one level above the
current buffer.  The command climbs twice, so it serves both sides
of one ladder:

1. A resource buffer opens the collection of its own type.  When
the resource belongs to a parent, the collection holds only the
rows of that parent, for example the servers of one project.
2. A collection buffer with a parent opens that parent resource.

The ladder of a server runs server, servers of its project,
project.  In show and list buffers, the keys =dired-jump= and
=dired-up-directory= run the command, so the keys that walk up a
directory tree walk up the resource hierarchy here.  The evil layer
remaps both keys too.

The parent comes from the =:parent= property of the resource
definition, so a mode needs no code of its own.  A server, volume,
image and network name their project.  A collection buffer without
a parent (a container, or a list opened on its own) sits at the top
level and signals =user-error=.  A scoped table has its own buffer
name, shows the parent in the mode line, and =gr= keeps the filter.
The parent ID comes from the show data of the buffer, so a climb
makes no extra CLI call.

* JSON view

=M-x openstack-json-view= (=J= in show and list buffers) opens a
read-only buffer with the parsed JSON of the last fetch, pretty
printed.  The data comes from the same fetch that drew the
display buffer, so the command makes no new CLI call.  A resource
buffer shows its hash table, a list buffer its array of rows.

The command shares the buffer: a second call switches to the
buffer it made before, and a refresh of the display buffer
redraws it in place.  =gr= in the JSON buffer redraws it from the
source buffer.  The buffer name is the display buffer name with a
=JSON= suffix, for example =*OpenStack Server* <id> JSON=.

* Resource types

The file =openstack-resources.el= holds every resource type, one form
each:

#+begin_src elisp
  (openstack-define-resource "volume"
    :noun "volumes"
    :id-prefix "volumes"
    :fields '("name" "status" "size")
    :list-fields '("ID" "Name" "Status"))
#+end_src

The macro in =openstack-mode.el= writes both modes
(=openstack-volume-mode= and =openstack-volume-list-mode=), their
display commands, fetchers and renderers, and the defcustoms of their
buffer names, field orders and list arguments.  The resource name
appears once, so the ID prompt, the two fetchers, the buffer names,
the dashboard URL and the type registry cannot disagree.

The optional keys of the form:

- =:cli= -- client resource command, when it differs from the type
- =:url-suffix= -- trailing dashboard URL segments (e.g. =/detail=)
- =:list-arguments= -- extra client arguments of =RESOURCE list=
  (e.g. =("--long")=)
- =:list-prefix-arguments= -- extra client arguments of
  =RESOURCE list= when the display command gets a prefix argument
  (the image list uses =("--all")=)
- =:parent= -- parent spec plist; =:type= names the resource type
  that owns the resource, =:field= the show field or fields that
  hold its ID, =:arguments= the client arguments that filter the
  list by the parent, with =:id= standing for the parent ID, for
  example =(:type "project" :field "project_id" :arguments
  ("--project" :id))=; =openstack-go-to-parent= reads it

The macro records the definition in =openstack-resource-definitions=
and adds the type to =openstack-resource-types=, so the ID prompts,
the Org links and the xref backend learn about it.  The order of the
forms is the order of that table.  =openstack-mode.el= ends with an
autoloaded =require= of the file, so an installed package fills the
registry at startup.

* Org links

The package ships the =openstack:= Org link type.  A link names
the resource type and the resource ID:

#+begin_src org
  [[openstack:server/b40b9091-4b4a-4a89-a1d1-2f0d6d1b8f01][web-1]]
  [[openstack:network/6f1e2d3c-0000-4000-8000-0000000000cc]]
#+end_src

Following a link opens the resource in its display buffer, like
RET on a list row.  =C-c l= in a display buffer stores a link
back to that resource; the link carries the resource name.  An
Org export renders the link as its Horizon URL.

Enable the link type in your init file:

#+begin_src elisp
  (with-eval-after-load \='org
    (require \='ol-openstack))
#+end_src

Customization (=M-x customize-group openstack=):

=openstack-resource-types= holds the resource type, display mode
and display command of each resource mode.  The resource modes fill
it when they load, so one entry there serves the ID prompts, the
Org links and the xref backend without a second list to update.

The export takes the dashboard URL from the mode's own
=openstack-id-prefix= and =openstack-url-suffix=, so the link
code never repeats those settings.

The =M-?= prompt completes the cached IDs.

* Evil bindings

The evil integration is optional and lives in =openstack-evil.el=.
The file requires evil 1.14 or later, but the package does not:
users without evil install nothing.  =package.el= compiles every
file during install, so an install without evil prints one
=Cannot open load file: evil= line.  The install still succeeds.
Install evil first to avoid the message.

#+begin_src elisp
  (require 'openstack-evil)
  (openstack-evil-mode 1)
#+end_src

The global mode binds keys in the normal and visual states of
OpenStack buffers and leaves the evil motions alone: =j=, =k=,
=gg=, =G=, =C-d=, =C-u=, =/=, =n= and =N= keep their meaning.
Evil state maps take precedence over a major mode map, so a mode
key such as RET or =q= needs a state binding to reach the buffer.

Show buffers keep the command keys of the mode: RET or
=<mouse-2>= opens the resource at point, =q= quits the window,
=gr= refreshes, =p= pops back to the origin buffer, =c= copies
the resource ID and =w= opens the dashboard page.  The evil
operators on those keys do nothing in a read-only buffer, so the
commands win.  The layer also remaps =dired-jump= and
=dired-up-directory= to =openstack-go-to-parent=, as the major
mode maps do.

List buffers treat a row as the unit: RET or =<mouse-2>= opens the
row, =c= or =Y= copies its ID, =w= opens its dashboard page, =q=
quits the window, =gr= refreshes and =S= sorts the current
column.  The evil motions stay untouched, so =j= and =k= move by
row and =n= and =N= repeat a search.  Select rows with =V= and
press =y= to copy the IDs of every selected row, one per line.
The command leaves visual state.

* Status, changes and notifications

Status values take a face: =ACTIVE=, =available= and =in-use=
green, =BUILD= and =REBOOT= yellow, =ERROR= red, =SHUTOFF= and
=DOWN= dimmed.  The map lives in =openstack-status-faces= and
the field names in =openstack-status-fields=.

Every face of the package inherits a standard one, so a theme
styles the buffers without extra setup: field names use
=openstack-field-name=, fetch errors =openstack-error=, a value
that changed =openstack-field-changed=, a date field named
in =openstack-date-fields= uses =openstack-date=, which inherits
=org-date=, and the resource ID uses =openstack-id=, which
inherits =marginalia-number=.  The ID face covers the =ID= line
of a detail buffer, its =id= field and the =ID= column of a
list.  Set one of them to restyle OpenStack buffers
without touching code buffers.

A field whose value differs from the previous refresh shows
=openstack-field-changed=.  The data comparison already skips
unchanged refreshes, so the mark only appears on a real change.

A status transition calls =openstack-state-change-functions=
with =:buffer=, =:id=, =:field=, =:old= and =:new=.  The hook
stays empty by default; add the shipped listener for messages
and desktop notifications:

#+begin_src elisp
  (add-hook 'openstack-state-change-functions
            #'openstack-notify-state-change)
#+end_src

A buffer with a transitional status polls every
=openstack-refresh-fast-interval= seconds instead of
=openstack-refresh-interval= seconds.  A server in =BUILD=
refreshes often; an =ACTIVE= server stays cheap.

* OpenStack CLI

The package interfaces with OpenStack through the
=python-openstackclient= command line program (nixpkgs package
=openstackclient-full=).  The Nix build substitutes the default
value of =openstack-program= with the store path of that program,
so users do not need to customize it.  The client needs standard
OpenStack authentication (e.g. an =openrc= file or environment
variables).

All CLI access goes through the =openstack-cli= library, which
mirrors the =jsonrpc= library's design: a synchronous
=openstack-cli-request= and an asynchronous
=openstack-cli-async-request=.

#+begin_src elisp
  ;; Synchronous: returns parsed JSON (hash table or list)
  (openstack-cli-request '("server" "show" "some-id"))

  ;; Asynchronous: callbacks when the process finishes
  (openstack-cli-async-request
   '("server" "list")
   :success-fn (lambda (result) ...)
   :error-fn (lambda (err) ...))
#+end_src

The =--format json= option is appended automatically.  Commands
that produce no output (e.g. =delete=) parse to nil; non-zero
exit or unparseable output signals =openstack-cli-error= (sync)
or calls =error-fn= (async).

* Library

Another package loads =openstack-data= alone and reads resources
without a buffer, a mode or a cloud.  The type string selects the
definition, so the client command, the list arguments and the
dashboard path come from one place:

#+begin_src elisp
  (require 'openstack-data)

  ;; Synchronous: the parsed JSON of `server show'
  (openstack-resource-show "server" "some-id")

  ;; Asynchronous: returns the client process
  (openstack-resource-list-async
   "project"
   (lambda (rows) ...)
   (lambda (err) ...))

  ;; Cancel an asynchronous call: neither callback runs
  (openstack-resource-cancel process)
#+end_src

The generated defcustom stays the runtime source of the list
arguments: set =openstack-container-list-arguments= and every
caller sees the new value.  =openstack-resource-list= takes one
optional argument, the extra client arguments that follow the
configured ones.  The same rule holds for the show field order
(=openstack-resource-fields=).

The cache lives in the data layer, so a prompt, a list buffer and
another package share one answer.  The cached entry points follow
=openstack-resource-cache-ttl=, and an invalidation call drops one
answer or every answer:

#+begin_src elisp
  ;; Cached, synchronous: no client call while the entry stays fresh
  (openstack-resource-list-cached "server")
  (openstack-resource-show-cached "server" id)

  ;; The rows only, stale or not: never calls the client
  (openstack-resource-cached-rows "server")

  ;; One list, one show answer, or the whole cache
  (openstack-resource-invalidate "server")
  (openstack-resource-invalidate "server" id)
  (openstack-resource-invalidate)
#+end_src

The interactive modes bypass the cache on purpose: a refresh must
show the cloud as it is now.  A cache change runs
=openstack-resource-change-functions= with one plist (=:type=,
=:id=, =:kind=, =:event=, =:old=, =:new=); an answer equal to the
cached one signals nothing.

The display layer turns data into text without a buffer, with the
field order, the value formatters and the faces of the definition:

#+begin_src elisp
  (openstack-resource-render "server" data)
  (openstack-resource-render "server" data id)
  (openstack-resource-render-list "server" rows)
#+end_src

The table string carries the columns of the list mode, the numeric
right alignment and the empty placeholder.  It has no faces.

The same split covers buffers: =openstack-buffer= builds the display
buffer and starts the refresh without selecting a window, and
=openstack-display= pops that buffer:

#+begin_src elisp
  (openstack-buffer id 'openstack-server-mode)   ; returns the buffer
  (openstack-display id 'openstack-server-mode)  ; pops it
#+end_src

Read a field without case, because =RESOURCE show= prints lower
case fields and =RESOURCE list= prints title case columns:

#+begin_src elisp
  (openstack-resource-id data)      ; the id of a show, the ID of a row
  (openstack-resource-name data)
  (openstack-resource-field data "status")
#+end_src

The data keeps the wire shape.  Pass the hash table on when the
exact keys matter.

Every error derives from =openstack-error=.  A failing client
signals =openstack-cli-error=, an unknown type signals
=openstack-resource-error=, and both stay catchable as
=openstack-error=:

#+begin_src elisp
  (condition-case err
      (openstack-resource-show "server" id)
    (openstack-error (message "%s" (error-message-string err))))
#+end_src

The registry holds the definition of each type
(=openstack-resource-definition=, =openstack-resource-arguments=,
=openstack-resource-fields=).  The table =openstack-resource-types=
adds the mode and the display command for the prompts, the Org
links and the xref backend.

The parent of a type comes from the same registry, so a consumer
climbs the hierarchy without a mode:

#+begin_src elisp
  (openstack-resource-parent-type "server")        ; "project"
  (openstack-resource-parent-id "server" data)     ; the project ID
  (openstack-resource-parent-arguments "server" id) ; ("--project" id)
#+end_src

A type without a single parent returns nil.  The command
=openstack-go-to-parent= reads the same functions.

* Design

=openstack-mode= is the base mode.  It keeps a buffer-local
=openstack--id=, renders a minimal view of the resource, and
provides ID handling.  Resource-specific modes (servers,
volumes, images, networks, ...) derive from it and set
=openstack-fetch-function= and =openstack-render-function= to
their own fetcher and renderer.  The fetcher of a generated mode
calls the data layer (=openstack-show-fetch= wraps
=openstack-resource-show-async=), so a mode and a library consumer
read the same data through the same definition.  The
=openstack-server= package
is the reference implementation of that contract:

#+begin_src elisp
  ;; openstack-server.el (excerpt)
  (defun openstack-server--fetch (id success-fn error-fn)
    "Fetch the data of server ID."
    (openstack-resource-show-async "server" id success-fn error-fn))

  (define-derived-mode openstack-server-mode openstack-mode
    "OpenStack Server"
    "Major mode for displaying an OpenStack server resource."
    (setq-local openstack-fetch-function #'openstack-server--fetch)
    (setq-local openstack-render-function #'openstack-server--render)
    (setq-local openstack-id-prefix "compute"))
#+end_src

The fetch runs asynchronously, so Emacs never blocks on the
client.  Display buffers refresh themselves through
=auto-revert-mode=, one fetch per =openstack-refresh-interval=
seconds (see =openstack-auto-revert=); =revert-buffer= (=g=)
forces a refresh.  Unchanged data is not re-rendered, so point
and marks survive a refresh.  The client authenticates on every
call; a token cache belongs to the native API layer, because an
`openstack' run validates its token against the identity server
anyway.

A display buffer shows data from a cloud, not a file: it starts
in =temporary-file-directory=, so =project.el=, version control
and language servers stay out of it.  The JSON view does the
same.

* Demo

The repository ships =mock-openstack=, a fake =openstack= client
emitting canned JSON, so the modes can be tried without a cloud:

#+begin_src elisp
  (require \='openstack-server)
  (setq openstack-program
        (expand-file-name "mock-openstack" "/path/to/repo"))
  (openstack-server-display "b40b9091-4b4a-4a89-a1d1-2f0d6d1b8f01")
#+end_src

* Building

#+begin_src sh
nix build          # one package, all modes
nix flake check    # ERT + lint + formatting
nix fmt            # nixfmt via treefmt
#+end_src

The build byte-compiles with warnings as errors and runs the ERT
test suite.  =nix flake check= builds the package derivation itself
(so the tests run there too) plus =checks.package-lint=,
=checks.checkdoc= and the treefmt formatting check.
`postPatch` rewrites `openstack-program` to the store path of the
nixpkgs `openstackclient-full` binary.  The version follows
=0-unstable-YYYY-MM-DD= from the last source commit.
